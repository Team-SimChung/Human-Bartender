일반 손님 외형 생성 시스템

1. 개요와 실행 시점

  • 외형은 1부에서 random_waves.json에 등록된 손님이 생성되는 순간 한 번만 결정한다.
  • 결정된 외형은 해당 손님이 퇴장할 때까지 유지하며 다시 추첨하지 않는다.
  • 카메오 손님(regular_slots.json)은 이 시스템을 사용하지 않고 캐릭터 전용 리소스를 사용한다.
  • 외형 생성 시스템은 확정한 성별과 슬롯별 파츠 ID를 GuestInstance에 전달한다.
  • 외형을 언제 저장하고 불러오기 뒤 어떻게 재사용하는지는 저장·불러오기 시스템을 따른다.

2. 데이터 — guest_bodies.json

{
  "gender": "m",
  "personality": "gentle",
  "slots": {
    "body": "body_m",
    "outfit": "outfit_m_7",
    "outerwear": null,
    "necklace": "necklace_m_1",
    "eyes": "eyes_m_1",
    "eyebrows": "eyebrows_m_2",
    "mouth": "mouth_m_1",
    "hair": "hair_m_2",
    "arm_accessory": "arm_accessory_m_1"
  },
  "current_emotion": "default"
}
  • 파츠는 종류에 따라 여러 슬롯으로 구분한다.
  • 배포되는 guest_bodies.json은 9슬롯을 슬롯별 배열로 담는다: bodies·outfits·outerwears·necklaces·eyes·eyebrows·mouths·hairs·arm_accessories + defaults·exclusions.
  • 남성 파츠는 실물 기준으로 등록되어 있다 — 의상 8 · 눈 3 · 눈썹 3 · 입 3 · 헤어 2 · 어깨 재킷 1 · 목걸이 1 · 팔 액세서리 1.
  • 눈썹과 입은 기본 바디에 합치지 않은 독립 슬롯이다. 아래 표를 파츠의 종류와 표시 순서를 정하는 구현 기준으로 사용한다.
  • GuestBodies 시트는 9슬롯 기준으로 확장되어 있다(32행).

  • 모든 파츠 PNG는 같은 기준점(pivot)·원점·발 위치로 정렬한다. 현재 남성 파츠의 캔버스 크기는 332×388이며, 여성 파츠도 남성과 같은 피벗과 레이어 정렬 기준을 사용한다.
  • 여성 파츠의 정확한 캔버스 크기는 정식 리소스가 나온 뒤 확인한다. 원본 크기가 남성과 다르면 엔진에 성별 예외 좌표를 추가하지 않고, 가져오기 전에 공통 캔버스로 정규화한다.
  • 엔진은 파츠별 위치나 크기를 별도로 보정하지 않고 모든 이미지를 (0,0) 좌표에 그대로 겹쳐 표시한다.
  • 투명 여백은 이미지의 위치를 맞추는 기준이므로 잘라내지 않는다.
  • 슬롯 종류와 레이어 순서는 데이터 빌드 스크립트(build.py의 part 검증 목록)와 엔진의 캐릭터 렌더러에 동일하게 등록한다.
  • 두 목록 가운데 하나만 수정하면 데이터 빌드는 통과하더라도 엔진에서 새로운 슬롯이 표시되지 않을 수 있다.
  • GuestBodies → part에 등록된 값이 정해진 슬롯 목록에 없으면 빌드 오류로 처리한다.
  • 슬롯을 추가하거나 순서를 변경할 때는 빌드 스크립트, 엔진 렌더러, 본 문서의 레이어 표를 함께 수정한다.

파츠 항목의 주요 필드

GuestBodies → part는 파츠의 슬롯을 구분한다. JSON으로 배포할 때는 bodies·outfits처럼 슬롯별 배열의 이름으로 변환된다.

{
  "id": "hair_m_2",
  "gender": "m",
  "personalities": [],
  "mode": "sprite",
  "sprite": "Guest/hair_m_2",
  "emotions": null,
  "parts": null,
  "weight": 1
}
  • id: 파츠의 고유 ID다. 금지 조합과 기본 조합이 이 값을 참조한다.
  • gender: 파츠를 사용할 수 있는 성별이다. m 또는 f를 사용한다.
  • personalities: 파츠를 사용할 수 있는 성격 목록이다. 빈 배열이면 모든 성격이 사용할 수 있다.
  • mode: 현재 일반 손님은 기본 외형 스프라이트 한 장만 표시하는 sprite를 사용한다. parts_anim은 후속 표정·애니메이션 리소스가 준비된 뒤 사용하기 위한 예약값이다.
  • sprite: 현재 빌드에서 반드시 필요한 기본 외형 이미지의 리소스 경로다.
  • emotions: 감정에 따라 교체할 이미지 목록이다. 표정 데이터 구조는 미리 유지하되, 현재는 모두 null이어도 정상 데이터로 인정한다. 자세한 규칙은 §6에서 설명한다.
  • parts: parts_anim을 사용할 때 필요한 애니메이션 파츠 정보를 저장한다. 후속 리소스가 나오기 전까지 null을 사용하며 빌드 오류로 처리하지 않는다.
  • weight: 파츠가 선택될 가능성을 조절하는 가중치다.
  • is_default는 원본 GuestBodies 시트에서 기본 파츠를 표시하기 위한 컬럼이다. 각 파츠 항목에는 배포하지 않고 guest_bodies.json → defaults로 변환한다. 컬럼은 시트에 등록되어 있다.

성격 데이터

손님의 성격은 외형을 만들기 전에 random_waves.json → personality에서 확정한다.

{
  "day": 1,
  "seq": 1,
  "order": "",
  "personality": "gentle",
  "delay_sec": 0,
  "max_rounds": 1,
  "branch_choice": false
}
  • 과거 tier 필드는 사용하지 않는다. 일반 손님의 성격은 현재 빌드에서 필수값이며 빈 문자열을 허용하지 않는다.

3. 생성 순서

순서단계규칙
1성격 확정random_waves.json → personality 값을 사용한다. 필수값이며 비어 있으면 빌드 오류로 처리한다.
2성별 선택데모에서는 m과 f 가운데 하나를 같은 확률로 선택한다. 이후 비율을 변경할 때 Config 값으로 분리한다.
3외형 선택§3.1에서 미리 만든 사용 가능한 조합 목록에서 가중치에 따라 완성 조합 하나를 선택한다.
4외형 적용선택한 파츠 ID를 손님 인스턴스에 기록하고 §2의 레이어 순서대로 겹쳐 표시한다.

3.1 사용 가능한 조합 목록

  • 게임이 데이터를 불러올 때 성별과 성격에 따라 만들 수 있는 모든 외형 조합을 미리 계산한다.
  • 각 파츠의 gender는 손님의 성별과 같아야 한다.
  • personalities가 비어 있거나 현재 손님의 성격을 포함한 파츠만 사용한다.
  • §4의 금지 규칙에 포함된 조합은 목록에서 제외한다.
  • 선택 슬롯(outerwear·necklace·arm_accessory)에는 조합을 계산할 때만 가상의 없음 후보를 추가한다.
  • 선택 슬롯을 사용하지 않은 결과는 손님 인스턴스에 null로 기록하며, 렌더러는 해당 슬롯의 레이어를 만들지 않는다.
  • 조합의 가중치는 포함된 모든 파츠의 weight를 곱해 계산한다. 값이 클수록 선택될 가능성이 높다.
  • 특정 성별과 성격에서 사용할 수 있는 조합이 하나도 없으면 데이터 오류로 처리한다. 빌드 단계에서 이를 확인하며, 게임 실행 중에는 금지 규칙을 임의로 무시하지 않는다.
  • 현재 파츠 수에서는 조합 목록을 미리 만드는 데 필요한 성능 부담이 크지 않다. 빌드 리포트에는 성별과 성격별로 생성된 조합 수를 출력한다.

3.2 중복과 선택 슬롯

  • 현재 바에 앉아 있는 다른 손님과 모든 슬롯이 같은 외형은 우선 후보에서 제외한다.
  • 중복을 제외한 뒤 선택할 수 있는 조합이 하나도 남지 않으면 중복을 허용하고 경고 로그를 남긴다.
  • 선택 슬롯의 없음 후보는 balance.json → config.guest_acc_none_weight(임시값 1)를 가중치로 사용한다.
  • 예를 들어 금지 조합의 영향이 없고 없음의 가중치가 1, 해당 슬롯의 실제 파츠 가중치 합이 3이면 그 슬롯을 사용하지 않을 확률은 25%다. 키는 Config 시트에 등록되어 있다(값 1).

4. 금지 조합(exclusions)

  • 특정 파츠 두 개가 한 손님에게 동시에 적용되지 않도록 데이터로 제한한다.
  • 예를 들어 특정 헤어가 의상의 깃과 겹치거나 두 파츠를 함께 사용했을 때 외형이 부자연스럽게 보이는 경우에 사용한다.
  • 원본 데이터는 LUNA_System.xlsx → GuestBodyExclusions 시트에 작성한다. 한 행에는 금지할 파츠 조합 하나와 그 이유를 기록한다 — 현재 팔 액세서리 6행.
part_apart_bnote
hair_m_2outfit_m_1헤어가 옷의 깃과 겹침
  • 금지 규칙을 파츠 데이터와 분리하면 한 행에서 조합과 이유를 함께 확인할 수 있으며, 같은 내용을 양쪽 파츠에 중복해서 작성하지 않아도 된다.
  • 빌드할 때 각 행은 guest_bodies.json → exclusions 배열로 변환한다. 검수용 note는 JSON에 포함하지 않는다.
{
  "exclusions": [
    {
      "a": "hair_m_2",
      "b": "outfit_m_1"
    }
  ]
}
  • a와 b의 순서는 결과에 영향을 주지 않는다. (a, b)와 (b, a)는 같은 금지 조합으로 처리한다.
  • 시트에 행이 없으면 exclusions는 빈 배열로 배포하며, 엔진은 이를 금지 조합이 없는 상태로 처리한다.

확정 금지 규칙 — 팔 액세서리(Acc_1)

  • Acc_1(팔 액세서리)은 민소매 상의에서만 노출한다. 현재 민소매 상의는 Shirt_3와 Shirt_3(2) 2종이다.
  • 따라서 Acc_1은 민소매가 아닌 나머지 상의 전부와 금지 조합이다. 시트에는 등록 id 기준 6행(arm_accessory_m_1 × outfit_m_1..6)이 들어 있다. 아래 표는 실물 파일명 기준 대조표다.

Acc_1Shirt_1(2)민소매 아님

  • 민소매 여부는 이미지를 보고 판단해야 하므로 데이터 검증으로 잡을 수 없다. 시트 작성자가 지킨다.

프로그래머 구현 방식

  • GuestBodyExclusions 시트의 각 행은 빌드할 때 guest_bodies.json → exclusions로 변환한다.
  • 엔진은 a와 b의 순서에 관계없이 같은 금지 조합으로 비교할 수 있도록 목록을 만들어 둔다.
  • 성별과 성격별 외형 조합을 만들 때 금지된 파츠 쌍이 포함된 조합은 제외한다.
  • 손님의 외형은 금지 조합을 제외하고 남은 조합에서만 선택한다.
  • part_a와 part_b에는 이미지 파일명이 아닌 GuestBodies 시트에 등록된 파츠 ID를 사용한다.

빌드 검증

  • 빌드할 때 아래 항목을 확인한다. 같은 조합을 중복으로 등록하거나 순서만 바꾸어 다시 등록한 경우에도 빌드 오류로 처리한다.
  • 빌드 리포트에는 성별과 성격별로 사용할 수 있는 조합 수를 출력한다.
검증 항목빌드 오류 조건
파츠 IDpart_a 또는 part_b의 ID가 GuestBodies 시트에 존재하지 않는다.
성별서로 다른 gender의 파츠를 금지 조합으로 등록했다. 두 파츠는 원래 함께 선택될 수 없으므로 불필요한 규칙이다.
슬롯같은 슬롯에 속한 파츠끼리 금지 조합으로 등록했다. 같은 슬롯의 파츠는 동시에 적용되지 않으므로 불필요한 규칙이다.
조합 생성 가능 여부특정 성별과 성격에서 사용할 수 있는 조합이 하나도 남지 않는다. §5의 기본 조합이 금지 조합에 포함된 경우도 여기에 해당한다.

5. 오류 및 예외 처리

  • 엔진은 어떤 상황에서도 금지 조합 규칙을 임의로 무시하지 않는다. 사용할 수 있는 조합이 없는 문제는 §4의 빌드 검증에서 미리 차단한다.
  • 데이터 손상 등으로 외형 선택에 실패하면 해당 성별의 기본 조합을 적용하고 경고 로그를 남긴다. 외형 생성 오류 때문에 게임 진행이 멈추어서는 안 된다.
  • 현재 기본 외형을 구성하는 필수 sprite 가운데 하나라도 불러오지 못하면 해당 손님의 외형 전체를 성별 기본 조합으로 교체하고 경고 로그를 남긴다. 문제가 생긴 슬롯 하나만 교체하면 새 파츠가 나머지 파츠와 금지 조합을 이룰 수 있기 때문이다.
  • 성별 기본 조합의 이미지까지 불러오지 못하면 일반 손님용 누락 리소스 이미지를 표시하고 오류 로그를 남긴다. 해당 손님의 게임 진행은 계속한다.
  • emotions 또는 parts_anim이 null이거나 요청한 표정·애니메이션 리소스가 아직 없는 것은 현재 제작 단계에서 허용되는 정상 폴백이다. 기본 sprite를 유지하며 빌드와 대화 진행을 막지 않는다.
  • 데이터에 선택 리소스 경로가 적혀 있으나 실제 파일만 누락된 경우에는 개발 로그를 한 번 남기고 기본 sprite로 폴백한다. 플레이어에게 오류 팝업을 표시하지 않는다.
  • 누락 리소스 이미지 발주 ❗

기본 조합

  • 각 성별의 필수 슬롯마다 기본으로 사용할 파츠 ID를 하나씩 지정한다. 데이터의 행 순서에 따라 기본값이 정해져서는 안 된다.
  • 원본 데이터에서는 GuestBodies → is_default로 표시하고, 빌드 결과는 guest_bodies.json → defaults에 성별과 슬롯별 ID로 저장한다.
  • 선택 슬롯은 모두 null로 지정한다.
{
  "defaults": {
    "m": {
      "body": "body_m",
      "outfit": "outfit_m_1",
      "outerwear": null,
      "necklace": null,
      "eyes": "eyes_m_1",
      "eyebrows": "eyebrows_m_1",
      "mouth": "mouth_m_1",
      "hair": "hair_m_1",
      "arm_accessory": null
    },
    "f": {
      "body": "body_f",
      "outfit": "outfit_f_1",
      "outerwear": null,
      "necklace": null,
      "eyes": "eyes_f_1",
      "eyebrows": "eyebrows_f_1",
      "mouth": "mouth_f_1",
      "hair": "hair_f_1",
      "arm_accessory": null
    }
  }
}
  • 기본 조합은 빌드할 때 다음 항목을 확인한다.
    • 모든 필수 슬롯에 기본 파츠가 지정되어 있어야 한다.
    • 각 성별과 필수 슬롯마다 is_default로 표시된 파츠가 정확히 하나여야 한다.
    • 기본 파츠의 personalities는 빈 배열이어야 하며 모든 성격에서 사용할 수 있어야 한다.
    • 기본 조합에는 금지 조합이 포함되어서는 안 된다.
  • 실제 이미지 파일이 존재하는지는 엔진이 데이터를 불러올 때 확인한다.
  • weight가 1보다 작거나 정수가 아니면 빌드 오류로 처리한다. 게임 실행 중에 값을 임의로 보정하지 않는다.
  • random_waves.json → personality는 필수값이며, 비어 있으면 빌드 오류로 처리한다.
  • 같은 웨이브에서 여러 손님이 생성되더라도 각 손님의 외형은 서로 독립적으로 선택한다.
  • 같은 손님이 max_rounds에 따라 여러 잔을 주문하더라도 처음 결정된 외형을 유지한다.

6. 표정·애니메이션 연동

현재 리소스 범위

일반 손님의 표정·파츠 애니메이션 리소스는 후속 3–4주 차에 제공될 예정이다. 현재 구현에 전달할 수 있는 리소스는 각 일반 손님의 기본 외형 스프라이트 한 장이며, 표정과 애니메이션이 없어도 1부 운영 전체가 정상 진행되어야 한다.

6.1 표정 데이터와 화면 표시

  • 대사에서 사용할 표정 ID는 외형 선택과 별도로 계속 결정한다.
  • 먼저 barks.json → expression을 확인한다. 값이 없으면 bark_situations.json → default_expression을 사용하며, 두 곳 모두 값이 없으면 default를 사용한다.
  • 표정 ID가 계산되더라도 guest_bodies.json → emotions에 대응 이미지가 없으면 화면에서는 기본 sprite를 그대로 유지한다.
  • 현재 emotions: null은 미완성 데이터가 아니라 기본 외형만 사용하는 현재 제작 단계의 정상값이다.
  • 표정 이미지가 없는 동안에도 대사, 인내심, 주문, 서빙 반응과 퇴장 상태는 데이터에 따라 정상 처리한다. 시각 이미지만 바뀌지 않는다.

6.2 애니메이션 폴백

  • 현재 일반 손님은 프레임 애니메이션 없이 기본 외형 스프라이트를 고정 표시한다.
  • 입장·퇴장에 최소 연출이 필요하면 캐릭터 전용 프레임 대신 공용 위치 이동·페이드와 같은 화면 연출을 사용할 수 있다.
  • 표정 전환이나 애니메이션 완료를 대사·상태 전이의 필수 완료 조건으로 두지 않는다. 선택 리소스가 없으면 기다리지 않고 다음 흐름을 진행한다.
  • 후속 리소스가 등록되면 emotions 또는 parts_anim 참조만 추가해 기존 표정 ID와 상태 호출을 그대로 사용할 수 있어야 한다. 별도의 대사 데이터나 운영 로직 수정이 필요해서는 안 된다.

6.3 리소스 판정 기준

구분현재 처리빌드·진행 영향
기본 sprite 존재기본 외형 한 장 표시정상
emotions·parts_anim이 null기본 외형 유지정상, 차단하지 않음
요청한 표정·애니메이션 키가 없음기본 외형 유지정상 폴백
선택 리소스 경로만 있고 파일 누락기본 외형 유지·개발 로그 1회진행 유지
기본 sprite 누락성별 기본 조합 또는 누락 리소스 이미지오류 로그, 진행 유지

7. 결과 기록

  • 손님 인스턴스에는 성별과 슬롯별 파츠 ID를 기록한다.
  • 표정 변경 기능을 사용할 때는 현재 감정도 함께 기록한다.
  • 사용하지 않는 선택 슬롯은 null로 저장하며, 렌더러는 해당 슬롯의 레이어를 만들지 않는다.
{
  "outerwear": null,
  "necklace": "necklace_m_1",
  "arm_accessory": null
}
  • 좌석 UI와 대사 출력 기능은 외형 정보를 직접 참조하지 않는다. 외형을 표시하는 렌더러만 이 정보를 사용한다.
  • 손님이 좌석을 떠나면 화면의 외형 인스턴스를 제거한다. 파츠 ID의 영속 보존 범위는 저장 시스템 문서에서만 관리한다.
  • 손님 생성·좌석·대사·저장 연결 순서는 1부 일반 손님 운영 런타임 명세을 따른다.

8. 결정 대기 ❓

  • 성별 비율: 데모에서는 남성과 여성을 각각 50% 확률로 선택한다. 이후 일차나 시간대에 따라 비율을 다르게 적용해야 할 때 Config 값으로 분리한다.
  • 여성 눈썹·입 아트: 실물이 없어 자리 파츠(eyebrows_f_1·mouth_f_1)로 채워 두었다 — 발주 ❗
  • 여성 파츠: 피벗·원점·발 위치와 레이어 정렬 기준은 남성과 동일하게 확정했다. 정식 리소스가 나오면 정확한 캔버스 크기만 확인하고, 규격이 다르면 가져오기 전에 공통 캔버스로 정규화한다.
  • 신규 슬롯: 귀와 같은 슬롯을 추가할 때는 빌드 스크립트의 슬롯 목록, 엔진 렌더러, §2의 레이어 표를 함께 수정한다. §3과 §4의 생성 및 금지 조합 규칙은 같은 방식으로 적용한다.
