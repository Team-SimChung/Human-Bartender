1부 일반 손님 운영 런타임 명세

목적

바 1부에서 플레이어가 바에 들어온 뒤 일반 손님이 생성·입장·착석하고, 성격에 맞는 대사를 하며 주문·제조·제공·퇴장을 거쳐 2부로 전환될 때까지의 런타임 계약을 정의한다.

1. 문서 범위

이 문서는 기존 칵테일 제조 문서보다 앞에 있는 일반 손님 운영 구간을 다룬다. 칵테일 선택·제조·기믹·판정·서빙 계산은 기존 하위 문서를 정본으로 사용하며 여기에서 반복하지 않는다.

영역이 문서의 책임외부 정본
진입·손님 큐개점 대화 종료 후 1부 시작 여부 판단, 당일 슬롯 병합random_waves.json · regular_slots.json
손님 생성성격·외형·좌석·주문 회차를 가진 GuestInstance 생성personalities.json · guest_bodies.json
대사·표정현재 상황과 성격에 맞는 대사 추첨과 표정 결정barks.json · bark_situations.json
대기·좌석코스터·서빙 인내심, 만석 대기, 좌석 예약과 해제balance.json → config
주문 이후기존 제조 루프로 전달하고 완료 결과만 수신1부 일반 손님 칵테일 제조 루프 기획서

핵심 원칙

일반 손님의 성격·성별·외형·주문 후보는 GuestInstance를 처음 만들 때 한 번 확정한다. 같은 손님이 추가 주문을 하는 동안에는 이 값을 바꾸지 않는다.

2. 바 입장부터 1부 진입까지

BAR_ENTER
→ 당일 바 배경·공용 UI 로드
→ bar_open 대본 실행
→ 당일 random_waves와 regular_slots 조회
→ 슬롯 0개: PART1_COMPLETE로 기록 후 즉시 2부
→ 슬롯 1개 이상: 1부 런타임 세션 생성 후 SPAWN_WAIT
  • bar_open 대사가 끝나기 전에는 일반 손님 생성 타이머를 시작하지 않는다.
  • 당일 슬롯이 없으면 빈 1부 화면을 잠시 표시하지 않고 2부로 전환한다.
  • Day 0은 현재 일반 손님 슬롯이 없으므로 개점 대화 뒤 바로 2부로 간다.
  • Day 3은 바 영업일이 아니며 1부와 2부를 모두 건너뛰고 다음 구간으로 이동한다.
  • 1부 완료와 2부 세션 시작은 각각 한 번만 커밋한다.

3. 당일 손님 큐 구성

3.1 슬롯 병합

  1. 현재 Day와 같은 random_waves.json 행을 가져온다.
  1. 현재 Day와 같은 regular_slots.json 행을 가져온다.
  1. 두 목록을 합쳐 seq 오름차순으로 정렬한다.
  1. 같은 Day에서 seq가 중복되면 순서를 임의로 정하지 않고 빌드 오류로 처리한다.
  1. day=99 QA 행은 실제 Day 99 테스트에서만 소비하며 데모 Day 0–3에는 포함하지 않는다.

3.2 생성 지연

  • 1부 시작 뒤 첫 슬롯은 balance.config.first_spawn_delay_sec만큼 기다린다. 현재 값은 5초다.
  • 첫 슬롯의 delay_sec가 0보다 크면 최초 지연 뒤 해당 값을 추가로 기다린다.
  • 두 번째 슬롯부터는 앞 슬롯의 입장이 확정된 시점을 기준으로 현재 슬롯의 delay_sec를 센다.
  • delay_sec가 비어 있는 예외 데이터는 spawn_delay_default_sec를 사용한다. 현재 값은 25초다.
  • 생성 순서는 앞 슬롯을 추월하지 않는다.

3.3 만석 처리

  • 지연시간이 끝났지만 빈 좌석이 없으면 슬롯을 SPAWN_BLOCKED 상태로 유지한다.
  • 대기 슬롯의 성격·성별·외형은 좌석이 실제로 확보되는 시점에 확정한다.
  • 좌석이 비면 reseat_delay_sec만큼 기다린 뒤 가장 앞의 대기 슬롯부터 입장시킨다. 현재 값은 10초다.
  • 대기 중인 슬롯을 제거하거나 뒤 슬롯과 순서를 바꾸지 않는다.
  • 제조 화면에 진입해 바 운영 타이머가 정지한 동안에는 손님 생성·재착석·인내심·잡담 타이머도 함께 정지한다.

4. 일반 손님 인스턴스 생성

4.1 생성 순서

슬롯 선택
→ personality 확정
→ gender 결정
→ 유효 외형 조합 선택
→ GuestInstance 생성
→ 빈 좌석 예약
→ 입장 연출
→ call 대사
→ WAIT_COASTER
  • 일반 손님은 random_waves.personality를 사용한다. 현재 빌드에서는 필수값이며 빈 문자열을 허용하지 않는다.
  • 데모의 성별 선택은 남성·여성 각 50%를 사용한다. 비율을 바꿀 필요가 생기면 Config로 분리한다.
  • 카메오 슬롯은 랜덤 외형을 만들지 않고 regular_slots.character가 가리키는 캐릭터 전용 리소스를 사용한다.
  • 외형 생성 세부 규칙은 일반 손님 외형 생성 시스템을 단일 기준으로 사용한다.

4.2 외형 선택

  1. 성별이 일치하는 파츠만 남긴다.
  1. personalities가 비어 있거나 현재 성격을 포함하는 파츠만 남긴다.
  1. exclusions에 포함된 금지 파츠 쌍을 가진 조합은 제거한다.
  1. 선택 슬롯에는 null 후보를 포함하고 guest_acc_none_weight를 적용한다.
  1. 현재 착석 중인 손님과 모든 슬롯이 같은 조합은 우선 제외한다.
  1. 중복 제외 후 후보가 없으면 중복을 허용하고 경고를 기록한다.
  1. 최종 파츠 ID를 GuestInstance에 저장하고 퇴장할 때까지 유지한다.

현재 모든 파츠의 personalities가 빈 배열이므로 성격에 따른 말투와 인내심은 달라지지만 외형 후보 풀은 성격별로 동일하다. 성격별 외형 차이가 필요하면 파츠 데이터에 허용 성격을 입력해야 한다.

5. 좌석 예약과 해제

  • 1부 좌석 ID는 L·M·R을 사용한다.
  • 현재 배치 우선순위는 화면의 왼쪽부터 L → M → R이다.
  • 입장 슬롯을 커밋하는 순간 좌석을 예약해 같은 프레임의 다른 손님이 중복 배정되지 않게 한다.
  • 입장 연출이 끝나면 예약 좌석을 점유 상태로 바꾸고 call 대사를 재생한다.
  • 퇴장 대사 시작 시점이 아니라 퇴장 연출이 끝난 시점에 좌석을 비운다.
  • 좌석 해제 뒤 대기 슬롯이 있으면 재착석 타이머를 시작한다.
  • 좌석 UI는 EMPTY·WAIT_COASTER·ORDER_DIALOGUE·WAIT_SERVE·REACTION·EXITING 상태를 구분한다.
  • 1부 카메라의 이동 시간·easing과 여러 손님 사이의 포커스 전환 연출은 바 내부 UI 문서에서 관리한다. GuestInstance는 카메라가 참조할 seat_id와 현재 발화자 ID만 제공한다.

6. 성격과 상황별 대사

6.1 선택 알고리즘

  1. barks.json에서 현재 situation과 같은 행을 모은다.
  1. 일반 손님은 voice_id == personality_id인 행만 남긴다.
  1. 성격 전용 후보가 없으면 voice_id = null인 공용 후보로 폴백한다.
  1. weight에 따라 한 행을 가중 추첨한다.
  1. 현재 언어의 text.ko 또는 text.en을 출력한다.
  1. {cocktail}은 현재 언어의 칵테일 이름으로 치환한다.
  1. 같은 상황에서 직전에 선택한 행과 다른 후보가 있으면 해당 행을 한 번 제외해 연속 중복을 줄인다. 후보가 하나뿐이면 중복을 허용한다.

카메오는 공용 폴백을 사용하지 않고 캐릭터 전용 voice_id 대사만 사용한다.

6.3 표정·애니메이션 처리

barks.expression
→ 값이 없으면 bark_situations.default_expression
→ 값이 없으면 default
→ guest_bodies.emotions 또는 parts_anim 확인
→ 대응 리소스가 없으면 기본 외형 sprite 유지
→ 대사와 운영 상태는 그대로 진행
  • 표정 ID와 애니메이션 요청 값은 후속 리소스 연결을 위해 현재도 계산하고 런타임에 유지한다.
  • 일반 손님의 표정·애니메이션 리소스는 후속 3–4주 차에 제공될 예정이며, 현재는 각 손님의 기본 외형 스프라이트 한 장만 사용하는 것을 정상 기준으로 삼는다.
  • emotions와 parts_anim이 null이거나 요청한 키가 없으면 기본 외형을 유지한다. 이는 데이터 오류가 아니며 대사, 인내심, 주문, 서빙 반응과 퇴장 흐름을 막지 않는다.
  • 일반 손님 전용 프레임 애니메이션이 없는 동안 입장·퇴장은 공용 이동·페이드 연출로 처리할 수 있다. 이 연출의 완료 여부를 표정 리소스 존재와 연결하지 않는다.
  • 후속 표정·애니메이션이 추가되면 기존 expression과 상태 호출을 그대로 사용하고 리소스 참조만 연결한다. 세부 폴백과 리소스 판정은 일반 손님 외형 생성 시스템을 따른다.

7. 인내심과 잡담 타이머

7.1 코스터 대기

coaster_limit
= clamp(coaster_base_sec × personality.patience_mult,
        coaster_min_sec,
        coaster_max_sec)
  • 입장 대사 call이 끝난 뒤 시작한다.
  • 50%에서 call_urge, 80%에서 call_final을 한 번씩 재생한다.
  • 유효한 코스터를 놓으면 즉시 종료하고 주문 대사로 전환한다.
  • 제한시간이 끝나면 leave_coaster와 이탈 결과를 한 번만 커밋한다.

7.2 서빙 대기

serve_bonus
= max(serve_min_bonus_sec,
      serve_bonus_sec - cocktail.unlock_day × serve_grace_per_day_sec)

serve_limit
= cocktail.time_limit_sec + serve_bonus
  • Order Cocktail이 확정된 뒤 시작한다.
  • 성격의 patience_mult는 코스터 대기에만 적용하고 서빙 대기에는 적용하지 않는다.
  • 50%에서 serve_urge, 80%에서 serve_final을 한 번씩 재생한다.
  • 제조 메뉴부터 결과 화면을 닫고 바에 돌아올 때까지 바 운영 타이머를 정지한다.
  • 제한시간이 끝나면 leave_serve 결과를 커밋하고 해당 손님을 퇴장시킨다.
  • 유효 코스터 드롭과 인내심 종료가 같은 프레임에 발생하면 balance.json → config.serve_timeout_same_frame_priority = timeout에 따라 인내심 종료를 먼저 커밋한다.
  • 이 경우 ServeResult를 생성하지 않고 손님을 퇴장시킨다. 해당 좌석의 코스터와 좌석에 귀속된 잔은 퇴장 연출 완료 뒤 함께 제거한다. 동시에 드래그 중이던 완성 잔은 서빙으로 소비하지 않고 서빙 대기 위치로 되돌린다.

7.3 잡담

  • 손님이 아무 대사·연출·주문 입력을 진행하지 않는 동안 idle_min_sec부터 idle_max_sec 사이에서 다음 잡담 시간을 추첨한다. 현재 범위는 8–13초다.
  • 잡담을 출력하면 새 시간을 다시 추첨한다.
  • 주문 대사, 반응 대사, 퇴장 연출, 제조 화면에서는 잡담 타이머를 정지한다.
  • 여러 손님의 잡담이 같은 프레임에 발생하면 좌석 순서 L → M → R로 하나씩 재생하고 나머지는 대기시킨다.

8. 주문·제조·퇴장 연결

  1. 코스터 드롭 후 ask_order를 출력한다.
  1. 일반 손님은 think_chance 추첨에 성공했을 때만 order_think을 출력한다.
  1. random_waves.order가 칵테일 ID면 해당 고정 주문을 사용하고 무작위 추첨은 실행하지 않는다.
  1. order가 비어 있으면 당일 해금된 status=confirmed 칵테일 후보를 balance.json → config.random_order_sampling_mode = uniform_with_replacement 규칙으로 추첨한다. 모든 후보의 확률은 같고 주문 회차마다 독립 추첨하므로 같은 손님이 이전 칵테일을 다시 주문할 수 있다.
  1. order 또는 reorder 대사와 함께 Order Cocktail을 확정한다.
  1. 주문별 order_id를 만들고 pending_orders[]에 추가한다.
  1. 이후 제조·서빙은 기존 제조 루프 문서를 따른다.
  1. 서빙 결과와 매출이 커밋된 뒤 round_index < max_rounds이면 같은 손님이 추가 주문을 시작한다.
  1. 추가 주문이 없으면 마지막 결과에 맞는 퇴장 대사를 출력한다.
  1. 퇴장 연출 완료 뒤 좌석·GuestInstance·코스터·해당 좌석에 귀속된 잔 리소스를 해제한다.
  1. 완료된 슬롯 ID를 1부 런타임 상태에 기록한 뒤 다음 슬롯 또는 1부 종료 조건을 검사한다.

틀린 칵테일도 서빙 결과와 반응을 정상적으로 처리한다. 1부 일반 손님의 이후 행동은 칵테일 제공·정산·다회 주문 문서를 따른다.

9. 런타임 데이터 계약

9.1 GuestInstance

아래 객체는 정적 JSON 파일이 아니라 한 명의 1부 손님을 추적하기 위한 런타임 구조다.

{
  "guest_instance_id": "rw_d1_s1",
  "source_type": "random_wave",
  "source_day": 1,

  • 제한시간과 남은 시간은 현재 실행의 메모리 상태로 관리하며 손님 퇴장과 함께 폐기한다. 영속 저장과 불러오기 기준은 저장 시스템 문서를 따른다.

9.2 저장 시스템 연결

이 문서는 GuestInstance의 런타임 역할만 정의한다. 저장할 필드, Part1Session 구조, 체크포인트, 비정상 종료 복구와 중복 결과 방지는 저장·불러오기 시스템을 단일 기준으로 사용한다.

10. 저장 시스템 경계

  • 일반 손님 운영 시스템은 손님의 생성·완료·1부 종료 이벤트를 런타임에 전달한다. Day 0 저장 정책은 바 최초 진입과 2부 시작 전환만 영속 저장하며, 손님 단위 이벤트로 자동 저장을 만들지 않는다.
  • 어떤 값을 영속 저장하고 어디부터 다시 시작할지는 이 문서에서 별도로 정의하지 않는다.
  • 저장 구조를 변경할 때는 런타임 명세에 구조를 복사하지 않고 저장·불러오기 시스템만 수정한다.

11. 오류와 검증

오류조건처리
PART1_SLOT_DUPLICATE_SEQ같은 Day의 공용 큐에서 seq 중복빌드 차단
PERSONALITY_MISSING일반 손님 personality가 비어 있거나 존재하지 않음빌드 차단
APPEARANCE_POOL_EMPTY성별·성격의 유효 외형 조합이 0개빌드 차단
APPEARANCE_RESOURCE_MISSING기본 외형을 구성하는 필수 sprite ID는 있으나 실제 리소스가 없음기본 조합 또는 누락 리소스 이미지 표시·오류 로그. 선택 표정·애니메이션 리소스 누락은 이 오류로 처리하지 않음
SEAT_DOUBLE_OCCUPIED같은 seat_id에 두 손님 배정두 번째 입장 취소·상태 복구
BARK_POOL_EMPTY상황·성격 후보와 공용 폴백이 모두 없음대사 생략·오류 로그, 필수 상황은 빌드 차단
PART1_RESULT_DUPLICATE같은 serve·settlement·exit 결과 재적용두 번째 요청 무시

빌드에서 다음을 확인한다.

  • Day·seq 중복과 잘못된 참조
  • personality 존재 여부
  • 고정 order의 칵테일 존재 여부
  • 카메오 character·scene·effects 참조
  • 성별·성격별 외형 조합 최소 1개
  • exclusions의 파츠 ID·성별·슬롯·중복
  • 필수 bark situation의 성격별 또는 공용 폴백
  • text.ko·text.en과 {cocktail} 치환 가능 여부
  • 기본 외형 파츠와 실제 리소스 경로

13. 현재 리소스 제약

  • 일반 손님 파츠의 personalities가 모두 비어 있어 성격별 외형 차이는 아직 없다.
  • 모든 emotions가 null이라 표정 판정은 가능하지만 외형 스프라이트는 바뀌지 않는다.
  • 여성 눈썹·입은 자리 파츠이며 여성 외형 조합 수가 적다.
  • 누락 리소스용 공용 이미지가 아직 필요하다.
  • 위 항목은 런타임 흐름 구현을 막지는 않지만 최종 시각 결과에는 영향을 준다.

14. 남은 결정

  • 1부에서 여러 손님 사이 카메라가 이동하는 시간과 easing
  • 향후 성격별 외형 제한 또는 파츠 가중치를 사용할지
  • 여성 파츠의 정확한 캔버스 크기 — 정식 리소스가 나오면 확인한다. 피벗·원점·발 위치와 레이어 정렬 기준은 남성 파츠와 동일하게 사용하며, 캔버스가 다르면 가져오기 전에 공통 규격으로 정규화한다.
