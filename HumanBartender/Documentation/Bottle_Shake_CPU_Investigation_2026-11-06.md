# 따르기 병 흔들기 CPU 급증 조사

기준일: 2026-11-06. Unity 6000.3.14f1 / Input System 1.19.0. 사용자가 확인한 조건은 **Unity 에디터 Play 모드에서 버튼을 누른 채 병을 빠르게 흔들 때**이다. 마우스의 실제 폴링레이트는 확인되지 않았다.

## 현재 판단: 사용자 검증 반영 (2026-11-07)

**사용자가 직접 검증하여 해당 Unity 마우스 입력 이슈 때문에 성능이 저하되는 것이 맞다고 확인했다. 이후 대응은 이 결과를 전제로 한다.** 이는 사용자가 실제 환경에서 확인한 결과이며, 아래의 자체 합성 입력 측정으로 원인을 재현했다는 뜻은 아니다. 사용자가 수행한 구체적인 비교 설정과 수치는 별도로 전달되지 않아 기록하지 않는다.

2026-11-06의 자체 검사에서는 합성 입력으로 급격한 CPU 상승을 재현하지 못했다. 이 검사는 실제 Windows 마우스 메시지 경로를 포함하지 않으므로 이후 사용자의 실제 환경 검증을 배제하는 결과가 아니다.

Unity는 Windows의 고폴링 마우스 이동 중 Play 모드가 크게 느려지는 문제를 공식 보고했다. 6000.3.15f1에서 재현됐다고 명시되어 있으며, 프로젝트의 6000.3.14f1 자체에 대한 재현 표기는 없다. 이슈에는 **에디터 쪽** 6000.3.29f1의 완화 수정이 기록돼 있지만 완전한 해결은 아니라고 설명한다. [Unity 공식 UUM-142550](https://issuetracker.unity.com/issues/19661/play-mode-framerate-drops-significantly-when-moving-the-mouse-cursor-with-high-polling-rate)

폴링레이트 변경은 사용자 장치 설정이므로 원인 분리 실험이나 임시 우회에 해당한다. 이를 배포 게임의 정식 수정으로 취급하지 않는다. 프로젝트는 이미 프레임당 한 번 포인터 위치를 읽고 있으며, 병 조작의 읽기 간격을 늘려 엔진의 실제 입력 메시지 처리 문제를 해결할 수 있다는 검증은 없다. 개발 측에서는 에디터와 Player 각각의 엔진 수정 적용 여부를 구분해서 확인해야 한다. 현재 조사에서 엔진 버전을 유지한 일반 C# 변경으로 이 이슈를 해결하는 방법은 검증되지 않았다.

## 추가 확인: 에디터와 실행 빌드 (2026-11-07)

**에디터에서만 발생하는 문제는 아니다.** Unity의 설명에 Standalone Player에서도 재현된다고 명시돼 있으며, Windows 실행 빌드에 대한 별도 이슈 UUM-147395가 있다. 이 빌드 이슈는 6.3.X에서 Open이고 7000.0.0a5에서 Fixed로 표시된다. 따라서 에디터의 6000.3.29f1 수정만으로 실행 빌드까지 해결됐다고 판단할 수 없다. [Windows Player 공식 이슈](https://issuetracker.unity.com/issues/23505/windows-player-framerate-drops-significantly-when-moving-the-mouse-cursor-with-high-polling-rate)

공식 재현 설명의 정지 상태 약 170FPS 기준 수치는 아래와 같다. 감소율은 보고된 근삿값을 기준으로 계산했다.

| 마우스 폴링레이트 | 마우스 이동 중 보고 FPS | 약 170FPS 대비 감소 |
| --- | ---: | ---: |
| 125Hz | 130FPS | 약 24% |
| 1,000Hz | 120FPS | 약 29% |
| 2,000Hz | 20FPS | 약 88% |
| 8,000Hz | 10FPS | 약 94% |

출처: [Unity UUM-142550 재현 설명](https://issuetracker.unity.com/issues/19661/play-mode-framerate-drops-significantly-when-moving-the-mouse-cursor-with-high-polling-rate). 이는 해당 재현 프로젝트의 수치이며, 이 프로젝트의 측정값이 아니다. 공식 페이지는 같은 조건에서 에디터와 빌드를 각각 측정한 별도 표나 CPU 사용률(%)을 제공하지 않는다. 따라서 빌드가 에디터보다 얼마나 덜 느린지, CPU 사용률이 몇 % 증가하는지는 이 자료로 산출할 수 없다.

이 프로젝트에서는 아직 실제 하드웨어 마우스를 사용한 Windows 실행 빌드의 급증 여부를 측정하지 않았다. 앞선 합성 입력 검사는 운영체제의 실제 RawInput 처리를 포함하지 않으므로 이 문제를 배제하는 근거로 쓰지 않는다.

## 코드에서 확인한 연결

```text
마우스 버튼: 누름/해제 때 병 잡기 상태 변경
  PourInputHandler.Update: 렌더 프레임당 포인터 위치를 한 번 읽음
    BottleTiltController.DragTo: 목표 각도 갱신
    BottleTiltController.Tick: 회전 속도 제한을 적용해 병 자세 변경

PourManager.Update
  StepSimulation: 120Hz 고정 스텝, 렌더 프레임당 최대 4회
    EmitFromNeck → SphSimulation.Tick → 유출 입자 회수
    2스텝마다 실제 잔에 남은 수량 측정
  GPU 입자 데이터 업로드
  출수 각도가 95도를 넘으면 반복 효과음 시작, 내려가면 종료
```

- 병 드래그는 입력 이벤트 개수만큼 SPH 물리를 호출하지 않는다. 같은 입자 상태라면 병의 각도 변경 자체가 물리 반복 횟수를 늘리는 구조도 아니다.
- 새로운 액체의 위치·속도는 방출 당시 병 자세에 따라 달라진다. 이 때문에 실제 출수 중에는 입자 수와 이웃 밀도가 달라질 수 있다. 이것은 같은 입자 수에서의 흔들기와 별도로 봐야 한다.
- 기존 SPH는 밀도 보정을 최대 3회 반복하며, 입자가 많아지면 CPU 부하가 크다. 낮은 FPS에서 프레임당 물리가 2회에서 최대 4회로 늘어날 수도 있다. 이번 조사에서는 물리 주기·수량 판정·목표선 설정을 바꾸지 않았다.

## 실제 프리팹 Play 모드 측정

사용 중인 에디터를 유지하고 `Logs/GimmickUiValidation/Project` 복제 프로젝트에서 Unity PlayMode 테스트 러너로 실행했다. 실제 `NewPourGame.prefab`, 병 입력 컴포넌트, HUD, 액체 렌더러, SoundManager와 사운드 클립을 사용했다. 메인 게임 자동 부팅은 복제 프로젝트에서만 잠시 껐다. 제조 중 주입되는 설정을 대신해 진단기에서 재료 beer, 용량 450ml, 최대 출수 설정 70ml/초와 기존 0.25 배율을 적용했다.

환경: Ryzen 5 7600 / RTX 4070 SUPER, D3D11, 1280×720 요청, 60Hz 시간 진행. 포인터는 Input System의 합성 Mouse 장치에 상태를 넣었다. 전체 Play 씬, 실제 하드웨어 마우스, 운영체제 RawInput 메시지 처리, 에디터의 실제 창 입력 이벤트는 재현하지 않았다.

아래 값은 프레임당 평균이다. SPH 열은 해당 렌더 프레임 안의 모든 물리 스텝 시간을 합친 값이다.

| 조건 | 입자 수 | 입력 큐 처리 | 병 포인터 전달 | SPH | 프레임 시간 95백분위 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 빈 잔, 잡고 정지 | 0 | 0.0123ms | 0.0100ms | 0.0005ms | 16.733ms |
| 빈 잔, 출수 없이 빠르게 흔들기 | 0 | 0.0132ms | 0.0060ms | 0.0005ms | 16.742ms |
| 위와 같은 흔들기, 입력 이벤트 100개/프레임 | 0 | 0.0381ms | 0.0054ms | 0.0005ms | 16.753ms |
| 액체가 있는 잔, 잡고 정지 | 242 | 0.0129ms | 0.0056ms | 2.9596ms | 17.050ms |
| 같은 액체, 출수 없이 빠르게 흔들기 | 242 | 0.0130ms | 0.0057ms | 3.1630ms | 17.645ms |

같은 입자 수에서 흔들기만으로 비용이 크게 뛰는 결과는 없었다. 합성 이벤트 100개/프레임도 약 60FPS를 유지했다. 이 결과로 실제 Windows 입력 처리 문제까지 제외할 수는 없다. 60FPS 유지 자체가 모든 CPU 사용량 증가가 없었다는 뜻도 아니다.

추가로 실제 물리 코어를 같은 초기 입자 상태로 비교했다. 의도적으로 과도하게 채운 1,600입자 시작 조건에서 프레임당 2스텝의 SPH 평균은 정지 15.88ms, 빠른 흔들기 15.69ms였다. 이 조건에서는 넘친 입자가 회수되어 마지막에 814개가 남았다. 정상 제조 FPS 예측에 쓰는 수치가 아니라, 병 각도 입력이 같은 물리 상태에 더하는 비용을 비교한 보조 검사이다.

## 효과음 반복 생성은 실제로 존재한다

`PourManager.Update`는 출수 경계에서 `pourSound`를 만들고 지운다. `SoundManager.StartLoop`는 매번 GameObject, AudioSource, 반복음 핸들과 페이드 코루틴을 생성한다. 종료 시 페이드가 남은 소스는 잠깐 유지되다가 제거된다.

이 경로를 분리하기 위해 입자 242개를 유지하고 추가 방출을 막은 상태에서 90도/110도 사이를 반복 조작했다. 효과음 켬 → 끔 → 다시 켬 순서로 비교했다.

| 조건 | 구간 길이 | 효과음 시작 횟수 | 시작 비용 합계의 프레임 평균 | 한 번의 시작 최대 비용 |
| --- | ---: | ---: | ---: | ---: |
| 효과음 켬 | 4초 | 29회 | 0.0141ms | 0.1717ms |
| 효과음 끔 | 4초 | 0회 | 0ms | 0ms |
| 효과음 다시 켬 | 4초 | 31회 | 0.0155ms | 0.1990ms |

기본 단발 효과음 풀 12개를 포함해 AudioSource는 최대 14개였다. 지속적으로 쌓이는 현상은 없었다. 최초 출수에서만 시작 비용이 2.3244ms였다. 반복 생성은 개선 가능한 낭비이지만, 이번 조건에서 지속적인 큰 CPU 급증의 주원인이라는 근거는 없었다. 이 마커는 메인 스레드 시작 비용이며 모든 오디오 스레드 비용을 뜻하지 않는다.

## 사용자 검증 이전에 제안했던 진단용 비교

1. 같은 액체 상태에서 출수 각도 미만으로 마우스만 빠르게 움직여 본다. 액체를 더 내보내지 않아도 급증하면 입자 증가와 별개인 경로다.
2. 마우스 제조사 프로그램에서 폴링레이트를 확인하고, 설정 가능하면 임시로 125Hz 또는 500Hz로 내려 같은 동작을 비교한다. 현상이 크게 줄어드는지 확인하면 실제 입력 경로를 좁힐 수 있다. 설정은 이번 조사에서 변경하지 않았다.
3. 실제 에디터 CPU Profiler에서 에디터를 대상으로 기록하고 `EditorLoop` 및 입력 처리와 `Pour.PointerDrag`, `Pour.Simulation`, `Pour.StartPourAudio`를 비교한다. 빈 씬에서도 마우스 이동만으로 같은 급증이 생기는지 비교하면 게임 코드 영향을 더 분리할 수 있다.

효과음을 기믹 동안 재사용하는 개선은 별도로 가능하다. 그 개선이나 물리 횟수 감소를 이번 Unity 입력 이슈의 해결책으로 간주하지 않는다.

## 증거와 변경 범위

- 최종 네이티브 PlayMode 진단: `Logs/BottleShakeInvestigation/play-instrumented-results.xml`, 1개 검사 통과. 10개 측정 구간, 워밍업 포함 2,260프레임 실행.
- 구간 요약: `Logs/BottleShakeInvestigation/runtime-results.json`
- 프레임별 기록: `Logs/BottleShakeInvestigation/runtime-frames.csv`
- 물리 코어 비교: `Logs/BottleShakeInvestigation/core-results.json`, 각 구간 CSV와 `core-valid.log`
- 재실행용 임시 진단 소스: `Logs/BottleShakeInvestigation/ProbeSources/`
- 초기 진단기의 실패 실행이나 초기 ProfilerRecorder 기록은 최종 수치에 사용하지 않았다. 관리 힙 할당량이나 GPU 시간은 이 조사 결과에 포함하지 않는다.
- 게임 런타임 코드·프리팹·입력 설정은 수정하지 않았다. 복제 프로젝트의 자동 부팅 설정은 측정 후 복원했다.
