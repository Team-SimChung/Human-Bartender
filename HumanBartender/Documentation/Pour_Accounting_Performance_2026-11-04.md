# 따르기 수량 판정 변경과 병 조작 프레임 드랍 분석

기준: 2026-11-04, Unity 6000.3.14f1. 실제 연결 프리팹은 `Assets/01.Game/03.Content/08.Prefabs/01.Crafting/02.Minigames/03.Pour/NewPourGame.prefab`이다. Pour와 FillUp이 같은 구현을 사용한다.

## 변경한 동작

기존 `PourManager.EmitFromNeck()`는 입자를 생성하기 전에 `유량 × 시간`을 `pouredMl`에 더했다. 입자 풀이 비었거나 액체가 잔에 도착하지 않았어도 수량이 증가하고, 넘친 양도 누적값에 남았다.

이제 입구에서는 입자를 생성하기만 한다. `SphVolumeTracker.Measure()`가 실제 도착한 입자를 측정하며, HUD·목표 도달·최종 `GimmickResult`는 모두 같은 수량을 사용한다.

```text
기울이기 → 실제 입자 방출 → 낙하 중: 0ml
  → 잔 바닥에 도착 / 이미 담긴 액체에 합류 → 수량에 포함
  → 잔 입구 위나 옆으로 유출 → 수량에서 제외

현재 ml = 도착 후 잔 안에 남아 있는 입자 수 × 입자당 ml
입자당 ml = 표시 용량 × spacing² × particleAreaScale / 잔의 월드 면적
```

- 빈 잔에서는 바닥과의 거리가 `spacing × 0.15` 이하일 때 최초 도착으로 인정한다. 충돌 반지름을 반영한 바닥 위치를 사용한다.
- 쌓인 액체 위에 붓는 경우에는 이미 도착한 입자의 SPH 이웃 중 거리 `spacing × 1.35` 이내, 속도 0.75 월드 유닛/초 이하인 입자를 받아들인다. 빠른 물줄기가 바닥까지 연결됐다는 이유만으로 공중 입자를 한꺼번에 세지 않는다.
- 도착한 입자는 잔 안에서 작은 파동이나 튐이 생겨도 양을 유지한다. 잔 밖으로 나가면 도착 상태를 해제하며, 재입장도 중복 누적하지 않는다. 입자 풀 재사용 때도 상태를 초기화한다.
- 수량 상한을 강제로 고정하는 방식이 아니다. 실제 남은 입자를 계산하므로 넘친 만큼 수량이 줄어든다. 거품·절차적 기포는 액체 입자가 아니므로 액체량에 포함하지 않는다.
- 물리는 기존 120Hz, 수량 측정은 두 물리 스텝마다 60Hz다. SPH 이웃 목록과 미리 확보한 탐색 버퍼를 재사용하며, 새로운 전체 입자 쌍 탐색이나 콜라이더를 추가하지 않았다.
- `quantityAccumulateMultiplier=0.25`는 방출 유량에만 적용한다. 입자당 용량에 다시 곱하지 않는다. 같은 입자·용량 환산을 쓰던 방출 간격과 목표선은 유지한다.

`따르기 마치기`는 출수와 추가 입력을 먼저 막는다. 최소 0.12초가 흐르고 도착 대기 입자가 없으면 결과를 확정하며, 물리 정리 시간 상한은 `finishSettleSeconds=1.5`다. 아직 도착하지 못한 입자는 상한 이후에도 결과에 더하지 않는다. 정리 중 `IsManualInputActive=false`이므로 `GimmickRunner`는 제조시간을 추가하지 않는다. 프레임당 물리 스텝 제한 때문에 낮은 FPS에서는 물리 정리 시간이 실제 벽시계 시간보다 길 수 있다.

## CPU 측정 결과

사용 중인 에디터가 프로젝트를 열고 있어 별도 임시 Unity 프로젝트에서 측정했다. 원본 프로젝트의 전체 런타임 C# 코드를 컴파일하고, Unity가 기본 어셈블리와 혼동하지 않도록 검증용 이름 `PourUnderTest.dll`로 로드했다. 의존 DLL도 원본 프로젝트에서 가져왔으며, 게임 코드를 더미 구현으로 대체하지 않았다. 에디터 코드와 테스트도 원본 프로젝트의 참조로 전체 컴파일했다.

Unity 6000.3.14f1, batchmode / nographics, Editor Mono에서 준비 후 SPH 60회·수량 측정 240회의 평균이다. 물성은 본편 Light와 같은 spacing 0.065, 밀도 반복 최대 3회이며, 두 배 스케일의 잔에 격자 형태의 입자를 배치했다. 전체 Play 씬의 화면·오디오·GPU 비용을 측정한 결과가 아니다.

| 활성 입자 수 | 기존 SPH 한 스텝 | 새 수량 측정 한 번 | 수량 측정 240회 관리 힙 할당 |
| ---: | ---: | ---: | ---: |
| 0 | 0.0003ms | 0.0002ms | 0바이트 |
| 256 | 1.4751ms | 0.0402ms | 0바이트 |
| 1,024 | 6.6398ms | 0.1488ms | 0바이트 |
| 2,000 | 13.2361ms | 0.3023ms | 0바이트 |

병 각도 갱신 `BottleTiltController.DragTo()`는 부모 Transform이 있는 조건에서 20,000회 평균 **0.000279ms**, 반복 할당 0바이트였다. 이 값에는 UI 레이캐스트·카메라 좌표 변환·입력 시스템 자체의 비용은 포함하지 않는다.

2,000입자 조건에서 수량 측정 1회는 물리 1스텝의 약 2.3%이고 빈도도 절반이다. 60FPS에서 매 프레임 물리 두 스텝을 돌린다고 가정하면 기존 SPH만 약 **26.47ms**, 새 수량 측정은 약 **0.30ms**다. 이는 측정 조건의 계산량을 환산한 예이며 실제 게임 FPS 예측값은 아니다. 플레이어 빌드, 하드웨어, 액체 배치·움직임에 따라 달라진다.

## 프레임 드랍에 대해 확인한 사항

### 액체가 쌓일수록 계속 느려지는 경우

기존 SPH 비용이 입자 수에 따라 크게 증가한다는 점을 CPU 측정으로 확인했다. `SphSimulation.CorrectDensity()`는 한 스텝에 최대 3번 공간 그리드·이웃·밀도를 다시 계산하며, 물리는 초당 120스텝을 목표로 한다. 최대 활성 입자 수 2,000은 단순한 표시 숫자가 아니라 실제 CPU 물리 부하다. 현재 변경에서는 조작감·수위에 영향을 주는 물리 주기나 밀도 반복 횟수를 임의로 낮추지 않았다.

다만 병을 놓자마자 입자 수가 그대로인데 FPS가 곧바로 회복되는 현상까지 이것 하나로 설명할 수는 없다. 물리는 병을 놓은 뒤에도 같은 입자에 계속 적용된다.

### 첫 출수 순간 한 번 크게 끊기는 경우

다음 비용이 첫 출수 프레임에 모이는 경로를 확인했다. 실제 끊김에서 각 항목이 차지하는 시간은 Game 뷰 Profiler 캡처가 필요하다.

| 경로 | 확인한 기존 처리 | 이번 조치 |
| --- | --- | --- |
| GPU 입자 버퍼 | 첫 입자에서 256개 용량을 생성하고 257/513/1,025개에서 폐기·재할당 | 기믹 시작 때 최대 용량을 예약. 2,000입자 설정은 2,048개, GPU 데이터 약 64KiB |
| 따르기 효과음 | `pour_loop.wav`가 사전 로드 꺼짐·백그라운드 로드 꺼짐. 첫 `AudioSource.Play()`에 로드가 겹칠 수 있음 | 해당 클립에 사전 로드·백그라운드 로드를 켬 |
| 루프 사운드 시작 | `SoundManager.StartLoop()`에서 GameObject와 AudioSource를 생성 | 시작 비용을 분리해 측정할 Profiler 구간 추가. 사운드 시스템 전체의 풀 구조는 변경하지 않음 |

오디오 백그라운드 로드가 메인 스레드 정지를 피하는 동작은 [Unity 공식 AudioImporter.loadInBackground 문서](https://docs.unity3d.com/kr/6000.0/ScriptReference/AudioImporter-loadInBackground.html)를 기준으로 확인했다. 클립의 실제 로딩·디코딩 시간을 이번 CPU 검사에서 측정한 것은 아니다.

### 입자가 없는 상태에서 잡기만 해도 느려지는 경우

`BeginDrag()`는 조작 상태와 목표 각도를 갱신하며, 이 시점에 입자 2,000개를 새로 만드는 구조가 아니다. 입자 GameObject 풀은 기믹 시작 시 만든다. UI 레이캐스트는 누르는 순간 1회 실행하고, 잡은 동안에는 포인터 좌표와 각도를 갱신한다.

기존에는 잡은 동안 무대 카메라를 매 프레임 부모에서 찾았다. 카메라를 캐시하고 부모가 바뀌면 갱신하도록 수정했다. `PointerEventData`와 UI 레이캐스트 결과 목록도 재사용한다. 이것들이 비정상적인 프레임 드랍의 확정 원인이라는 의미는 아니다.

튜토리얼에서는 잡는 동안 `StoryTutorialController.UpdateGimmick()`가 안내 UI를 숨기는 경로도 있다. 화면이 바뀌는 첫 프레임의 Canvas 재구성과 첫 액체 렌더링의 셰이더·드라이버 비용은 이번 nographics 검사 대상 밖이다.

## 실제 Game 뷰에서 원인을 구분할 위치

CPU Profiler에서 다음 구간을 따로 볼 수 있도록 마커를 추가했다.

| 마커 | 확인할 비용 |
| --- | --- |
| `Pour.PointerPress` | 최초 누름의 UI 레이캐스트·드래그 시작 |
| `Pour.PointerDrag` | 잡은 동안 포인터 좌표 변환·각도 전달 |
| `Pour.Simulation` | 기존 SPH 한 스텝 |
| `Pour.MeasureRetainedVolume` | 새 도착/유출 수량 판정 |
| `Pour.StartPourAudio` | 따르기 루프 사운드 시작 |
| `Pour.AllocateParticleBuffer` | 버퍼 생성. 정상적으로는 기믹 시작 시 한 번 |
| `Pour.UploadParticles` | 입자 데이터 업로드 |
| `Pour.BuildRenderCommands` | 렌더 명령·효과 텍스처 구성. GPU 실행 시간 자체는 별도 GPU Profiler로 확인 |

비교 구간은 ① 빈 잔에서 정지 ② 출수 각도 미만으로 잡기만 함 ③ 첫 출수 ④ 많은 입자로 계속 따름 ⑤ 같은 입자 수에서 놓음이다. Deep Profile은 우선 끄고 비교한다. 이번 작업에서는 사용 중인 Unity 창의 조작이나 실제 Play 씬의 FPS·GPU 캡처를 수행하지 않았다.

## 검증과 파일

- 전체 런타임·에디터 C# 컴파일 성공.
- Unity EditMode 검사 **16개 통과, 실패 0개**. 빈 출수, 실제 중력 낙하 후 바닥 도착, 수면 합류, 빠른 물줄기 제외, 넘침·재입장, 풀 재사용, 스케일·회전된 잔, 표시 단위·배율, 마치기 대기·상한, CPU 비용·반복 할당을 검사했다.
- 원본 에디터의 열린 씬을 전환하거나 저장하지 않았다. 검증 프로젝트와 XML·로그는 `.gitignore` 대상인 `Temp/PourValidation/`을 사용했다. Unity의 Temp 정리로 삭제될 수 있으므로 최종 통과 수와 측정값은 이 문서에 기록했다.
- 테스트 소스: `Assets/01.Game/06.Tests/Editor/SphVolumeTrackerTests.cs`, `PourAccountingTests.cs`, `PourPerformanceTests.cs`. 원본 프로젝트에서도 EditMode Test Runner로 같은 클래스를 실행할 수 있다.
- 핵심 구현: `PourManager.cs`, `Sph/SphVolumeTracker.cs`, `Sph/SphParticle.cs`, `Sph/SphContainerBoundary.cs`.
- 입력·첫 출수 비용 조정: `PourInputHandler.cs`, `SphLiquidRenderer.cs`, `pour_loop.wav.meta`.

이 변경은 실제 액체를 기준으로 수량을 바로잡고 확인된 초기 할당·로드 경로를 조정한다. 프레임 드랍이 완전히 해소됐다는 검증은 아직 없으며, 위 구간의 실제 Game 뷰 측정으로 지속 SPH 부하와 최초 출수 지연을 구분할 수 있다.
